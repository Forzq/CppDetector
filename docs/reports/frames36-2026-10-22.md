# Локальная проверка frames36 — 22 октября 2026

Это исходный прогон до изменения геометрии и переноса изображений в фон. Последующая реализация и актуальное время до вердикта описаны в [новом отчёте](geometry-and-verdict-2026-10-22.md).

Текущий C++ код укладывается в бюджет 500 мс на 10 камер в этом локальном прогоне. Основные проблемы обнаружились в настройке стыка и критерии отбраковки: неверная линия стыка даёт нестабильные результаты, а порог площади 2% пропускает небольшие области, которые алгоритм уже выделил.

Исходные кадры и `config/config_frames36.json` сохранены без изменений. Подготовлен отдельный [конфиг с исправленной линией стыка](../../artifacts/frames36-study/config_seam_candidate.json). Код инспекции не менялся.

## Что проверено

- Все 1000 JPEG, 10 камер, 1224×1024; 990 сравнений после исключения собственного эталона каждой камеры. Для камеры 4 сохранён эталон `f_0000003`, для остальных — `f_0000001`.
- 42 варианта настроек × 390 входов = **16 380 сравнений**. Каждый вариант: 18 выбранных реальных кадров и 21 искусственный/контрольный вход на камеру. Выборка охватывает переходы между изделиями и вторую съёмку.
- **9240 измерений стыка**: две линии × 35 вариантов × 132 входа. На каждую линию — все 100 реальных кадров камеры 4, 30 локальных изгибов, плавный изгиб и локальная подмена участка стыка.
- **795 измеренных партий по 10 камер**, 24 комбинации режима/масштаба/потоков, плюс прогрев. Отдельно проверены встроенный тестовый дефект и периоды 100/300/1000 мс.

Искусственные изменения сделаны средствами OpenCV с известными размерами: пятна радиусом 2/4/8/16/32/64 px, царапины шириной 1/3/7 px, удаление печати, слабое изменение яркости, изменение только цвета, сдвиги 2/8/20 px, поворот 1°, изменение освещения, JPEG и пятно на фоне. Стык деформировался переносом реальных пикселей вместе с окружением. Сохранены входы и наложения результатов.

Это исследовательские контрольные изменения, а не размеченный набор реальных производственных дефектов. Например, удаление печати не создаёт осмысленный дефект на однотонном внутреннем дне ведра. Число срабатываний на этих входах нельзя считать производственной полнотой обнаружения.

## Условия измерения скорости

Локальный Docker Desktop/WSL на AMD Ryzen 5 5600GT, 12 доступных потоков, контейнеру доступно около 7,44 GiB RAM. GCC 13.3.0, `-O3 -DNDEBUG`, OpenCV 4.6.0, Ubuntu 24.04. На машине не было готового MSVC/OpenCV; зависимости установлены внутри Docker, системный C++ toolchain Windows не устанавливался.

Эти числа относятся к локальной Linux-сборке. Нативная Windows/MSVC-сборка с OpenCV 4.14 не измерялась. Файловый кэш прогрет. Захват с физических камер, транспорт основной программы и HTTP здесь не участвуют.

«Полный App» — настоящий `App::loop`/`tick`: чтение JPEG, инспекция, стык, полноразмерное наложение, JPEG результата, JSONL и сохранение изображений брака с существующим ограничением частоты. Эмуляция проверялась через публичный API класса, без браузера. В начале каждой серии исключены три партии прогрева. Времена ниже — wall time всей партии, мс; это не сумма времён десяти потоков.

Во всех **795 измеренных партиях превышений 500 мс — 0**. Длинная серия при 0,5/1 поток включает полный проход набора с отсутствующей этикеткой и второй съёмкой. Остальные серии App короче и проходят первые кадры; серии ядра используют стратифицированную выборку всего набора.

На этой машине принудительное ограничение OpenCV одним потоком не улучшило полный цикл. Поэтому менять число потоков только по общему предположению о конкуренции потоков не стоит.

При 0,5 ядро значительно быстрее полного App. Снижение до 0,35 даёт сравнительно небольшой выигрыш полного цикла и заметнее теряет мелкие изменения. Следующий резерв скорости тестовой программы — отрисовка/кодирование наложений: сейчас они выполняются для каждого кадра. Разность времён отдельных серий — ориентир, а не точное профилирование отдельных функций.

## Как влияют настройки основной инспекции

В следующей таблице «зона» означает пересечение прямоугольника найденной области с прямоугольником внесённого изменения. Это не попиксельная оценка точности. Проверено 120 контрольных изменений на десяти камерах; в колонках брака учитывается основная инспекция отдельно от стыка. 135 реальных кадров — часть выборки вне диапазона отсутствующей этикетки, включая внутренние камеры.

| Изменение относительно исходного конфига | Изменений с выделенной зоной / 120 | Изменений с браком / 120 | Реальных кадров с браком / 135 |
|---|---:|---:|---:|
| Исходные настройки: sens=0,5, порог=2%, shift=3, blob=20, scale=1 | 75 | **2** | 8 |
| Только sensitivity=1 | 104 | **2** | 41 |
| Только reject_threshold=0,05% | 75 | **54** | 39 |
| Только shift_tolerance=0 | 78 | 2 | 40 |
| Только shift_tolerance=10 | 74 | 2 | 0 |
| Только min_blob_area=1 | 90 | 2 | 9 |
| Только min_blob_area=2000 | 21 | 2 | 3 |
| Только downscale=0,5 | 62 | 2 | 1 |
| Только downscale=0,35 | 58 | 2 | 0 |
| Автоматический ROI | 38 | 2 | 18 |
| Вместе: scale=0,5, sens=0,75, порог=0,05%, blob=5 | 75 | 54 | 34 |

Последняя строка — исследованный пример настройки для мелких дефектов, не готовый универсальный рабочий профиль: вместе с чувствительностью растёт число срабатываний на реальных кадрах. Полные результаты всех 42 вариантов: [таблица](../../artifacts/frames36-study/sweep.csv), [сводка JSON](../../artifacts/frames36-study/variants_summary.json).

| Параметр | Проверенные значения/режимы | Наблюдаемый эффект |
|---|---|---|
| `sensitivity` | 0; 0,25; 0,5; 0,75; 0,9; 1 | Понижает порог разности от 80 до 5 уровней серого. Больше зон и реакций на небольшие изменения положения/печати. Сам по себе не отменяет порог площади 2%. |
| `reject_threshold` | 0; 0,01; 0,05; 0,1; 0,5; 1; 2; 5% | Меняет итоговый брак, но не карту разности и не найденные зоны. Сравнение строгое: `score > threshold`. |
| `shift_tolerance` | 0; 1; 3; 5; 10; 15; 30 | Расширяет диапазон допустимых значений около деталей эталона; скрывает небольшие несовпадения и часть дефектов печати. Также меняет предел грубого сдвига `max(4×tolerance, 8)`. |
| `min_blob_area` | 1; 5; 20; 100; 500; 2000 | Удаляет небольшие связные области после морфологии. Уменьшение помогает выделять мелкие зоны, но при 2% итоговый брак почти не меняется. |
| `downscale` | 0,1; 0,2; 0,35; 0,5; 0,7; 1 | Основной регулятор скорости ядра. Мелкие/тонкие дефекты теряются из-за уменьшения, размытия и морфологии. |
| ROI | сохранённый; весь кадр; автоматический; отдельный полигон текста камеры 4 | Меняет и контролируемую область, и знаменатель score, и нормализацию яркости. Автоматический ROI нельзя принимать без визуальной проверки: на этих видах он может выбирать обод/светлый участок и исключать место дефекта. Полигон текста камеры 4 ухудшил обнаружение отсутствующей этикетки на выборке с 5/5 до 0/5. |
| Эталон | сохранённый ранний; кадр 378 | Другой эталон заметно меняет реакции между двумя съёмками. Поздний эталон — отдельная исследовательская серия; её искусственные изменения всё ещё сделаны на раннем изображении, поэтому она не измеряет чистое обнаружение дефекта относительно нового эталона. |
| Встроенный `defect` | выключен / включён на собственном эталоне каждой камеры | **0/10 брака** при включении: score 0–0,86%, ниже 2%. Отсутствие брака при этой галочке не означает, что наложение не произошло. |

`shift_tolerance` и `min_blob_area` заданы в рабочих пикселях. При scale=0,5 допуск 3 соответствует примерно 6 исходным пикселям, а blob=20 — примерно 80 исходным пикселям площади. Поэтому уменьшение масштаба при неизменных числах дополнительно ослабляет обнаружение мелких дефектов.

Изменение только цвета при сохранении яркости не обнаруживается: сравнение идёт в grayscale. Внесённое изменение яркости на 15 уровней также не выделилось при пороге разности около 42. На камере 4 удалённая печать дала score=0 при исходных настройках и около 0,564% при sensitivity=1 — всё ещё ниже 2% для брака.

## Стык камеры 4

Сохранённая линия `(424,283) → (245,649)` проходит через другую часть этикетки и захватывает настоящий тонкий стык лишь частично. На 80 реальных кадрах с этикеткой линия найдена 41 раз, и все эти 41 измерение дают брак; остальные 39 теряют стык. На самом эталоне coverage≈0,493, поэтому он тоже не находится. Это объясняет нестабильность возле порога coverage=0,5.

Отдельно проверенная линия **`(393,225) → (250,633)`** находится на **80/80** кадрах с этикеткой с **0/80** брака по стыку. На 20 кадрах без этикетки линия не найдена; отсутствие этикетки отклоняет основная инспекция.

| Изгиб 4 px в середине | **брак**; ratio≈3,71 |

Стык не является проверкой полного совпадения с эталоном: плавная геометрия допускается, локальные отклонения измеряются относительно гладкой кривой. Если линия не найдена, сам модуль стыка не бракует кадр. Это существующее поведение, его нужно учитывать при работе с очень слабым/разорванным стыком.

## Что имеет смысл применить

1. Для камеры 4 использовать отдельно подготовленные координаты стыка; band=30, tol_mid=1, tol_edge=5, edge_frac=0,12 оставить как проверенную отправную точку. Основной конфиг автоматически не изменён.
2. Для сохранения мелких деталей исходный scale=1 уже проходит локальный бюджет времени. Scale=0,7 — проверенный вариант ускорения, но качество по маленьким дефектам нужно оценивать вместе с допусками и фильтрацией областей. Scale=0,1/0,2 для тонких деталей по этому прогону не подходит.
3. Если нужен брак по небольшому пятну/царапине, текущий глобальный порог 2% нужно пересматривать. Одного повышения sensitivity недостаточно. Проверенный профиль 0,5/0,75/0,05%/5 показывает эффект, но увеличивает реакции на реальные кадры и не годится как общий автоматический пресет.
4. ROI проверять визуально по каждой камере; отдельные полигоны для печати и других зон требуют проверки и мелких дефектов, и отсутствующей этикетки. Переключать эталон между разными съёмками без повторного контроля нельзя считать нейтральным изменением.
5. Для дальнейшего развития полезны отдельный критерий по локальной зоне и отрисовка по запросу. Изменение только цвета потребует дополнительного цветового признака. В рамках этой проверки алгоритм не менялся.
